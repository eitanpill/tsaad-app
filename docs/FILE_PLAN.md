# File and route plan: צעד קטן ביום

This plan was written in stage 0. Each stage builds only the files assigned to it, and a security gate and an accessibility gate run between every two stages.

## Stack
- Next.js 16 with the App Router, TypeScript and a `src/` directory. The UI is Hebrew and right-to-left.
- Postgres on Neon (`@neondatabase/serverless`) in production and node-postgres (`pg`) for local development and tests, both through drizzle-orm. `src/db/index.ts` picks the driver from the host in `DATABASE_URL` (localhost means `pg`; the check in `src/db/local-url.ts` also rejects `?host=`/`?hostaddr=` overrides). drizzle-kit generates the migrations as SQL in `drizzle/`, and they are committed.
- Vercel hosts the app, and Vercel Cron runs the scheduled jobs.
- Accounts use opaque sessions stored in the database. Passwords are hashed with argon2id (`@node-rs/argon2`).
- `zod` validates the environment, the webhook payloads and the forms. `web-push` sends push messages, using VAPID keys.
- There is no auth framework and no date library. Time zone handling uses `Intl` with Asia/Jerusalem.

See `docs/CONTENT.md` for where the day content and the Bunny video ids (`BUNNY_VIDEO_IDS`) live.

## Routes
| Route | Kind | Who can reach it |
|---|---|---|
| /login, /activate, /forgot, /tsaad, /legal, /legal/accessibility, /legal/privacy, /legal/terms, /account/deleted | page | anyone (`/activate` needs a valid one-time link; the legal texts are DRAFT, see `docs/LEGAL_REVIEW.md`) |
| /today, /path, /day/[n], /live, /reminders, /install, /offer, /yesodot, /account | page | a logged-in user |
| POST /api/webhooks/ghl/signup | handler | callers with `GHL_WEBHOOK_SECRET` (header `x-tsaad-webhook-secret`, or HMAC signature plus timestamp); 503 if the secret is unset or shorter than 32; 5-minute window when a timestamp header is sent; idempotent by event id; no `Origin` check (server to server) |
| login, forgot, activate, logout | server actions (`src/app/(auth)/actions.ts`) | login and forgot are open but rate-limited (a locked-out username sees a message pointing to "שכחתי סיסמה", whose link works during the lockout and lifts it once used); a database failure while creating the session shows the friendly "משהו לא עבד" error; every action checks `Origin` against `APP_ORIGIN`; logout deletes the session row. There are no `/api/auth/*` handlers; handlers added later use `rejectCrossOrigin` |
| GET /api/video/[day] | handler | a session, and only once the server has unlocked that day |
| GET /api/live/[day]/ics | handler | a session; day 7 or 14 only, and only when `START_DATE` and `LIVE_TIME_DAYn` are set (else 404). The join link is not in the file |
| POST/DELETE /api/push | handler | a session, `Origin` check, rate limit, subscription validated (see Stage 9) |
| POST /api/push/status | handler | a session, `Origin` check, size limit; no rate limit (read by key, called on each app load) |
| GET /manifest.webmanifest, /sw.js, /offline.html | static / metadata | anyone (no personal data; the service worker caches no HTML) |
| GET /api/cron/reminders, /api/cron/sync, /api/cron/cleanup | handler | requests that carry `Bearer CRON_SECRET` (constant-time check; 401 if the secret is unset or shorter than 16 characters) |
| POST /api/csp-report | handler | anyone (browser CSP reports); log only, rate-limited per instance, no DB (stage 11) |
| GET /go/[offer] | handler | anyone; `offer` is `challenge`, `session`, `bundle` or `yesodot` and nothing else. Counts one click (`offer_clicks`, no personal data) unless it is a HEAD, a browser prefetch/prerender (`Purpose`, `Sec-Purpose`, `X-Moz`, `Next-Router-Prefetch`), a known bot or link preview, or over a light in-memory limit (3 per offer per IP hash per 10 minutes; without a trusted IP, 120 per offer per instance; `lib/offer/click-limit.ts`), and always answers 302 to the matching `MORNING_URL_*` (with the UTM parameters as before); 404 when the key is unknown or the URL is unset. No input of the request reaches the target |
| /admin/stats | page | a logged-in user whose username is in `ADMIN_USERNAMES`. Everyone else, logged in or not, gets the normal 404 page with a real 404 status, decided in `proxy.ts` before anything streams (`lib/stats/admin-gate.ts`: one session lookup, only on `/admin` paths and only when a session cookie is present; fails closed). The `/admin` layout checks again. Server-rendered, aggregate numbers only, noindex |
| /admin/participants | page + server actions | same gate as /admin/stats. Manage participants (list/search, add by hand, new one-time link, disable/enable via `users.disabled_at`, delete) and the owner-only day preview cookie (`lib/preview`, HMAC with SESSION_SECRET bound to the admin account, re-verified per request). Actions: Origin + admin + rate limit (`lib/admin/guard.ts`), audit lines with ids only |
| GET /api/share-card?m=N | handler | anyone; renders the finish card (PNG, 1080x1350, next/og) from a 14-bit mask of counted days. Only `m`, in canonical form, and only a completed mask (12+ days, so at most 106 images); anything else is 400. Cached for a year (`immutable`) and kept in memory per instance. No cookies, no name, no tracking, no DB. Hebrew is laid out for satori by `lib/share/visual-hebrew.ts` (numbers, Latin and punctuation inside a Hebrew word stay correct). The Today finish tile's "שתפו" button fetches it (same origin) and shares it with the Web Share API, else downloads it. Fonts: `src/assets/fonts` (OFL TTFs; satori cannot read woff2). |
| GET /api/health | handler | anyone; `{ok, db}` only (200, or 503 when the database is unreachable), `no-store`, result memoised 5 s |

Access is enforced in the data-access layer (DAL) and in each route handler, not only in `proxy.ts`. The page never receives the content of a locked day.

## Tables
| Table | What it holds |
|---|---|
| `users` | Accounts: lowercase unique `username` (enforced by a CHECK), display name, email, phone, nullable `email` (phone-only signups) and `phone` (E.164 for GHL signups), nullable unique `ghl_contact_id`, nullable `password_hash` (null until activation), `created_at`, `activated_at`. There is no `must_change_password` flag. |
| `activation_tokens` | One-time activation and reset links (`purpose` is `activate` or `reset`). Only the SHA-256 hash of the token is stored, with `expires_at` and `used_at`. |
| `sessions` | Login sessions. Only a hash of each token is stored, with `created_at`, `expires_at` and `last_seen_at`. |
| `login_attempts` | Failed logins and other rate-limited attempts. Stores hashes of the identifier and IP, never the raw values, and no link to a user (the unused `user_id` column was dropped in migration `0008`). |
| `offer_clicks` | Aggregate counters of clicks on the offer buttons, one row per offer and local day (`clicks`). No user, IP or browser data; not tied to `users`. Read by `/admin/stats`. |
| `webhook_events` | Incoming webhook event IDs (unique; a hash when derived from the contact id), used to make the signup webhook idempotent; purged after 30 days. No personal data. |
| `action_completions` | Completed actions (`habit`, `move`, `meditate`, `live`), unique on (user, day, action), day 1 to 14. |
| `push_subscriptions` | Browser push subscriptions, endpoint unique. |
| `reminder_log` | Reminders, unique on (user, date), with status `pending` (written before sending), `dry_run`, `sent` or `failed`. |
| `sync_outbox` | Updates waiting to be synced, with status (`pending`, `failed` = will retry, `sent`, `dead` = gave up), attempts, next attempt time (also used as a lease while a worker holds the row) and an optional unique dedupe key. |

Every table that holds personal data references `users(id)` with `ON DELETE CASCADE`, so deleting an account removes all of its data. This is covered by an integration test.

Accounts are activated through a one-time link: the participant sets their own password, and nothing temporary is ever issued.

Live attendance has a single source of truth: `action_completions` with action `live` on days 7 and 14 (the tracker payload reads it; the unused `live_attendance` table was dropped in migration `0006`).

Completion of the challenge (12 of 14 days) is calculated when needed and not stored.

Measurement is cookieless and first-party only. Signed up, activated, active per day, returned and days counted are derived from `users`, `action_completions` and `push_subscriptions` (`src/lib/stats/queries.ts`); only offer clicks have their own counter (`offer_clicks`, migration `0009`). "Returned on day N" means the user marked something on day N and also on an earlier day; visits themselves are not recorded.

## Config, CI and tooling
- All environment reads go through `src/config` (`getConfig()`, and `readEnv()` for the raw source after validation). `src/config/single-source.test.ts` fails if another file reads `process.env` (the allow-list: client code, `proxy.ts`, `instrumentation.ts`, the logger).
- Times in texts (`{unlockTime}`, `{reminderTime}`) are filled from `UNLOCK_HOUR` and `REMINDER_TIME` (`src/lib/times.ts`); a test forbids a hard-coded HH:MM in the copy.
- `npm run typecheck` runs `next typegen` first, so it works on a fresh clone.
- `.github/workflows/ci.yml`: one job (typecheck, lint, unit tests, migrate and run the database tests against a Postgres 16 service, build with dummy env) on every push and pull request with cancel-in-progress; an optional Playwright job on the default branch and on manual runs.
- Fonts are variable fonts via `next/font` (Noto Sans Hebrew: hebrew; Rubik: hebrew and latin), one file per subset rather than per weight. The Bunny player iframe loads only after a click on the play button (`src/app/(app)/today/VideoTile.tsx`).

- **Stage 9א, GHL link:**
  - the signup webhook, with a shared secret, idempotency and replay protection
  - it never resets an existing user
  - `api/health`: not built in this pass (still open)
  - built:
    - `app/api/webhooks/ghl/signup/route.ts` (POST only) over `lib/webhooks/ghl/{auth,payload,normalize,username,signup,delivery,handler}.ts`. Migration `0006`: `users.email` nullable, `login_attempts.kind` gains `webhook`, table `live_attendance` dropped.
    - Auth (`auth.ts`): `GHL_WEBHOOK_SECRET` (min 32; unset or short = 503, nothing is processed). Header `x-tsaad-webhook-secret` alone is enough (GHL's Custom Webhook action can only send static headers). Optional `x-tsaad-timestamp` (unix seconds) plus `x-tsaad-signature` (hex HMAC-SHA256 of `timestamp.` plus the raw body bytes, optional `sha256=` prefix). Every credential presented must be valid; when a timestamp is present, it must be within 5 minutes (both ways), for the static header too, which is shorter than the 30 days `webhook_events` are kept. All comparisons constant-time (`constantTimeEqual`). No secret in a query string.
    - Order: secret configured (503), trusted-IP block after repeated auth failures (429), size (413, 16KB, read incrementally), auth (401), content type (415), JSON and zod (400), configuration (503), transaction, response. Failures per trusted IP are counted in `login_attempts` (kind `webhook`, HMAC keys; 20 per 15 minutes); without a trusted IP header there is no per-IP limit (the long secret is the defence).
    - Body (`payload.ts`): `contact_id`/`contactId`/`id`, `first_name`/`last_name`/`full_name` (and camelCase), `email`, `phone`, optional `event_id`/`signup_id` (top level or in `customData`). Empty and null are missing, unknown fields ignored, an invalid email or phone is dropped, and at least one valid of the two is required. Email lowercased; phone normalised to E.164 (`+972…`, many Israeli formats; other international numbers with `+`/`00` kept).
    - Idempotency (`signup.ts`): one transaction with an advisory lock per contact id; the event id (a hash of contact id plus `x-tsaad-event-id`, so a constant header value cannot block other contacts; else a hash of contact id plus the optional marker) is inserted first (unique), a repeat returns `duplicate`. Same contact id: activated gives `exists` (nothing changes, logged); not activated gives a fresh link that invalidates the old one (`reissued`), at most 3 per hour per contact, then `exists`. Without a per-event id or marker, the same contact always maps to the same derived id, so a second signup is a `duplicate`; to allow a re-issue GHL must send an event id or marker (see `docs/GHL_SETUP.md`).
    - Username rule (`username.ts`): the email local part, lowercased, ASCII-folded, `[a-z0-9._-]`, 3 to 20 characters, and not a reserved staff-like name (`admin*`, `support*`, `tsaad*`, `root`, ...); otherwise the national phone digits (`0521234567`); last resort `yogi` plus 5 digits. A collision gets a numeric suffix (`dana`, `dana2`, `dana3`) up to 50, then a random 6-digit suffix (20 tries). Chosen because it is short, memorable and recognisable to the participant, and needs no counter table; uniqueness is enforced by the `users.username` unique index (`ON CONFLICT DO NOTHING` and retry). `display_name` is the GHL name through an allowlist (letters, marks, space, apostrophe, hyphen, maqaf, gershayim; no digits, URLs, brackets, bidi or zero-width characters, NFC, max 80), else the username. Only username, display name, email, phone and contact id are stored.
    - Response: `{ok, status: created|reissued|exists|duplicate}` (200), `{ok:false, error}` otherwise, always `Cache-Control: no-store`; never a token or personal data. Delivery runs in `after()`, after the commit.
    - Delivery port (`delivery.ts`): `SignupDelivery.deliver({userId, ghlContactId, username, link, expiresAt, messages})`, with the messages already composed from `copy.messages.activation` (WhatsApp if there is a phone, email if there is an address; `[START_DATE]` filled from `START_DATE`). The only adapter is dry-run: it logs kind, channel, user id and lengths, never the link or contact details. A guarded e2e-only capture adapter (same guard as the test clock, plus `TSAAD_WEBHOOK_CAPTURE_FILE`) writes the link to a file for Playwright. A delivery failure is logged and does not change the response; the participant can use "forgot password".

      - (a) The adapter calls the GHL API (private-integration token, contact update) to write the link into a contact custom field, which triggers a GHL workflow that sends the WhatsApp and the email. ## Security and accessibility gate on the owner decisions round
- `lib/ghl/client.ts`: the contact update sends `customFields: [{id, fieldValue}]` when `GHL_FIELD_*_ID` is set, else `[{key, fieldValue}]` (GHL's schema: `id` required, `field_value` deprecated); never `tags` in the PUT. 429/408/5xx carry `Retry-After` (seconds or date, capped at 1 h) into the outbox delay (`markFailed` `minDelaySeconds`). A temporary failure removing the tag before a re-arm stops the send (else the workflow would not fire). `createGhlClient` refuses to build without an injected fetch under tests/e2e.
- `lib/ghl/outbox.ts`: claims in chunks of `GHL.claimChunk` (5) within `GHL.runBudgetMs` (60 s), so a chunk always ends well inside the 5-minute lease (no second claim and double send of a link). A direct link delivery cancels a waiting retry of the same purpose (`cancelQueuedLink`), so a stale retry cannot replace the fresh link. `enqueueLink` honours `Retry-After`.
- `lib/auth/login.ts`: an exact username match wins over a phone match, so a username made of phone digits keeps working when another account shares the phone.
- WhatsApp opt-out: migration `0012` adds `users.whatsapp_reminders` (default true). `lib/ghl/preferences.ts`, `app/(app)/reminders/{actions.ts,WhatsappToggle.tsx}`: a `role="switch"` on /reminders ("תזכורת בוואטסאפ", `copy.reminders.whatsappTitle`), shown only when `GHL_REMINDER_MODE` is not off and the user has a GHL contact; same-origin, session, per-user rate limit (`toggle`). `queueGhlReminders` skips users who switched it off, and the worker drops a queued row if they switch it off later.
